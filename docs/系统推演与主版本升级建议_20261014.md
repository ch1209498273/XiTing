# 系统推演与主版本升级建议

日期：2026-10-14。基线：当前工作区 v5.0.1/code88。状态：供评审的升级建议，尚未实施。

## 结论与目标

建议以“在播放器里完成听剧准备、操作与结束”为下一次主版本主线。用户可感知的升级应是：正在看视频时就能确定播放目标和设置定时；黑幕后操作可靠；到期、失效、中断都有明确结果；日常入口延续 v4 的直观方式。

此前 v5.0 的方案将后台状态、场景和诊断直接放到主界面，同时改变主按钮语义、统计顺序与设置组织。它增加了学习成本，关键播放器兼容问题却没有先通过真机验收。这是产品与验证次序的问题，需要调整升级方法。

保留本地、轻量、原生 Android、无 INTERNET 权限、八语言、现有成长与数据规则。界面以用户认可度较高的 v4 为参照，当前 v5.0.1 是纠偏后的技术基线，并不表示整体体验已经获得认可。

## 本轮证据范围

本轮完成当前代码检查、16 个场景的分支推演，以及既有测试日志和真机记录核对。没有操作手机、重新测量声音或耗电，也没有修改产品代码。场景推演用于确定验证顺序，不能作为本轮真机测试通过的证据。

- `v5.0.1体验纠偏记录_20261013.md`、`uat-v501-20261013/physical-checks.json`：此前真机验证了安装、UI启动、服务/悬浮球、开启与退出黑幕；本轮播放器名称和音频复验未完成。
- `uat-v50-20261013/physical/README.md`：此前哔哩哔哩短时黑幕声音连续由用户确认；切回本应用配置定时后目标不可见，定时暂停没有真正启动。
- 既有单测、核心设备用例及布局日志通过，但布局矩阵主要断言尺寸并绘图，不能证明每个动态弹窗、每个控件和真实播放器路径可用，也不能证明美观。

## 系统当前的四个瓶颈

| 瓶颈 | 当前证据 | 对用户的影响 | 结论边界 |
|---|---|---|---|
| 跨应用切换破坏准备流程 | 哔哩哔哩真机记录；定时面板在打开时获取活动会话，确认时再查询 | 视频仍能听，但回到本应用后无法选择目标，睡前定时流程断开 | 现象已记录；播放器、系统和查询时机的各自原因仍待定位 |
| 播放目标和设置结果缺少一致契约 | `NowPlaying.kt:66` 显式选择失效后会自动寻找其他会话；`TimerDialogs.kt:186` 提交后关闭；服务 `OverlayService.kt:951` 仍可拒绝 | 普通播控可能换到另一个应用；弹窗关闭也未必表示定时生效 | 代码分支可达，需独立复现；已有定时到期动作仍绑定原始目标，不应误称其会自动换应用 |
| 新状态层尚未统一执行 | `SessionCoordinator` 接收状态更新，`TimerController` 保存字段；服务仍执行校验、调度、结束与通知 | 每增加一个操作入口，都要协调更多分支和刷新路径 | 是结构检查结论，不代表当前每条路径都出错；应围绕新增操作收敛职责 |
| 验收覆盖与交付结论不匹配 | 布局矩阵、合成媒体会话通过；真实播放器定时、长时后台、耳机/来电、耗电未通过 | 测试数量增加，仍可能留下用户第一步就遇到的问题 | 保留已有有效测试，补实际路径证据，不重写为全面通过 |

补充发现：无媒体时首页来源行整体隐藏，`PlaybackSources` 将查询异常返回为空列表；成功体验确认目前没有形成持久的已完成状态。用户可能分不清“没有播放”“未授权”“会话失效”，成功后也仍看到首次体验入口。

## 16 个场景推演

“已有验证”指此前对应证据；“代码推演”指检查分支所得；“待实测”不能当作兼容结论。

| ID | 用户场景 | 当前表现与证据 | 新版应达到的结果 |
|---|---|---|---|
| S01 | 首次安装，仅开悬浮窗权限 | 基础黑幕不依赖媒体读取；播控能力受可选权限限制 | 用户能先使用黑幕；启用暂停/片尾时再说明实际依赖 |
| S02 | 点击十秒演示 | 演示可在本应用上遮幕，成功问答要求用户确认 | 将“操作演示”和“真实播放器声音/返回验证”分别记录；完成后收起首次引导，可再次访问 |
| S03 | 日常启动→回播放器→点击球→返回 | 此前短时黑幕和纠偏版启动/返回分别有证据 | 保持 v4 主按钮语义与既有手势；基本路径不增加步骤 |
| S04 | 哔哩哔哩播放中，切回本应用设定时 | 真机已有目标不可见记录 | 优先验证在播放器仍可见时绑定与配置；无有效会话时明确不支持的动作 |
| S05 | 同时存在两个播放器，已选目标随后失效 | 普通播放信息查询可能回退另一会话，代码推演 | 显式选择后保持选择；失效显示失效，用户重新选择前不发送到另一目标 |
| S06 | 撤销媒体读取权限或查询抛错 | 可能得到相同空结果，来源行隐藏 | 区分未授权、没有会话、失效、查询失败；每种只给一个适用的下一步 |
| S07 | 点击确定到服务处理之间目标消失 | UI会复查，服务也会复查；UI提交后立即关闭 | 服务确认“已设置”才显示成功；拒绝时保留输入和原定时，不留下假成功 |
| S08 | 定时已设置，目标到期前销毁 | 定时目标对象保持原会话，不重新选择；已有合成回归 | 原目标不可用则报告未完成；不得暂停另一应用；做双播放器真实回归 |
| S09 | 请求暂停并保留黑幕，到期有/无反馈 | 已有最多5秒确认与结果存储；UI提示字段与结果快照分开维护 | 所有入口使用同一结果；区分已请求、报告暂停、未确认，黑幕期间不弹亮屏提示 |
| S10 | 听完本集时暂停、倍速、拖动或换集 | 已有计算、观察与换集取消逻辑及合成回归 | 保留现有规则，用真实播放器逐项验证；不将缺失进度当作可用片尾定时 |
| S11 | 首页/黑幕/通知交替延长、取消、停止 | 多入口已有实现，状态由服务发布 | 同一命令入口、明确受理结果；重复操作幂等，定时/通知/黑幕状态一致 |
| S12 | 来电、耳机断开、恢复音频 | 已有撤幕与音频模式监听；真机覆盖不足 | 验证实际打断、到期碰撞和返回；明确哪些动作取消/保留，避免自动恢复未经确认的播放 |
| S13 | 系统回收进程、重启、重新打开 | 已有检查点/中断结果/恢复说明，旧目标不恢复 | 不补计未知时长，不重放旧媒体动作；能看到发生过中断和下一步 |
| S14 | 大字体、横屏、长应用名、弹窗打开时重锁 | 布局尺寸矩阵已有；实际动态列表和操作覆盖不完整 | 实际打开动态面板，检查控件边界、点击、滚动、返回、5秒重锁；默认/1.5倍字体分别验收 |
| S15 | 助手空闲一小时，黑幕连续两小时或过夜 | 服务启动就持有最长10小时唤醒锁；未有耗电对照 | 建立空闲/黑幕/定时分场景基线，再调整持锁与刷新；不凭计数宣称节电 |
| S16 | 从v4.3.1或v5.0.1升级、恢复旧备份、操作失败回退 | 已有多格式备份与回退测试；手机可见字段曾保留 | 保留历史、成长、成就、佩戴和偏好；用旧版本样本与失败恢复验证，不清数据解决升级问题 |

## 路线选择

| 路线 | 收益 | 代价 | 建议 |
|---|---|---|---|
| 继续逐项修补界面 | 改动小，适合纠偏 | 无法解决跨应用准备与结果确认 | 仅作为维护项 |
| 围绕听剧流程贯通升级 | 播放器内设置、目标稳定、结果明确；现有能力形成完整体验 | 需先验证真实播放器，再收敛执行入口 | 采用 |
| 重做播放器或整体框架 | 控制自己的媒体链路更充分 | 内容来源、版权/登录与第三方限制是另一类产品问题；迁移成本大 | 当前范围不采用 |

## 统一优先级与升级范围

P0：开始扩展功能前先通过。P1：主版本必需能力。P2：核心流程稳定后的体验与性能。P3：需求验证后的独立扩展。新工作与已有能力分开列，不把已有功能重复算作升级成果。

| 顺序 | 优先级 | 工作包 | 实际增量 | 依赖及验收 |
|---|---|---|---|---|
| 1 | P0 | 播放器可行性与目标契约 | 定位哔哩哔哩会话丢失；复现显式目标失效后的普通播控回退；区分无权限/无会话/失效/错误 | 首先用当前OPPO与哔哩哔哩验证；另一个已有媒体应用作为错发检查。黑幕、暂停、进度、片尾分别记录，不能用应用名加载成功代替播控成功 |
| 2 | P0 | 设置结果确认与基线保护 | 定时命令增加受理/拒绝结果；固定v4快速操作和已有数据口径；补具体失败用例 | 复现UI检查通过后服务拒绝的时序；拒绝保留输入/原定时；同目标重复操作不重复结算 |
| 3 | P1 | 播放器内听剧面板 | 在原黑幕唤醒层补“设置定时”，除延长/取消外可选15/30/60分钟、自定义及可用的本集结束；确认显示目标、时长、结束动作 | 先做可行性探针：面板不得造成可闻停顿、焦点丢失或会话销毁。捕获与绑定有效目标，已失效的token不能靠缓存变有效 |
| 4 | P1 | 统一会话操作与结束结果 | 将设置/延长/取消/停止与结果处理收敛到同一命令执行入口；通知、小组件、首页、黑幕只展示结果 | 在新增流程涉及范围内渐进拆分服务；保留已有单调时钟、原目标、5秒确认、恢复与回退逻辑，避免同时重写整个架构 |
| 5 | P1 | 打断与恢复闭环 | 将来电/耳机/权限撤销/进程回收/重启与定时到期组成明确的行为表；失败提示对应下一步 | 真机验证事件碰撞及中断后返回；已确认的规则各入口一致；原因未知保持未知 |
| 6 | P2 | UI完整定稿与首次成功流程 | 延续v4三个页签及精灵位置；统一播放器选择、定时、结果反馈的排版；真实首次验证完成后收起引导；缺失能力有可操作空状态 | 先给首页、定时、播放器选择三页预览；再看实际安装图。常用操作不增加点击；失败说明用户能理解；八语言/主题/大字体动态路径通过 |
| 7 | P2 | 分场景耗电与响应优化 | 空闲减少无效任务与重绘；依据实测缩短不必要持锁；按需更新媒体信息/通知 | 连续使用通过后做同设备、相近内容/网络/亮度、无充电对照；先报告原始结果和差异，不预设节电百分比。ROM不稳定时保留可回退策略 |
| 8 | P2 | 按播放器记住常用设置 | 记住用户选择的时长与结束动作，减少重复输入 | 仅保存偏好，不持久化媒体token；每次新目标仍须有效性检查。旧偏好不静默启动已失效定时；确有重复使用需求后加入 |
| 9 | P3 | 精灵、成就、海报、更多统计及主题扩展 | 根据实际使用反馈决定 | 现有成长与成就完整保留；新皮肤、勋章、回顾和场景入口不挤占本次主流程资源 |

备份兼容、迁移和精灵/成长不回退属于每批共同验收要求，不作为新的“大功能”包装。诊断留在帮助/故障流程中按需进入。

## 目标交互

推荐日常路径：

1. 按原方式启动助手，打开常用播放器开始播放。
2. 点原悬浮球进入黑幕；保持已有退出和移动手势。
3. 需要定时时，唤醒操作层并设置；面板只展示目标应用、时长、结束动作及必要失败原因。取消回到原状态。
4. 服务接受设置后，显示“已设置：30分钟后请求暂停哔哩哔哩，保持黑幕”等具体结果；无受理不显示成功。
5. 到期按原目标执行；下次主动唤醒时显示最终反馈。停止助手时清理资源；返回画面与停止助手仍是不同操作。

此流程是设计目标。尤其步骤2–3的会话可用性须通过P0探针。若黑幕打开本身就销毁目标，会话缓存和更换查询时机都不能保证控制恢复；该播放器可提供的功能必须按实测限制。不能用全局PLAY_PAUSE冒充原目标暂停成功。

| 页面 | 保留的使用习惯 | 本次允许的呈现变化 |
|---|---|---|
| 首页 | v4主按钮、定时快捷入口、统计及三个底部页签 | 条件式单行来源或问题提示，不重新堆叠控制台和三场景卡 |
| 播放器选择 | 应用名、图标、明确选择 | 内容标题作为次行；失效原因与重选入口；无包名占主视觉 |
| 定时/黑幕面板 | 单次设置、延长/取消、明确返回 | 显示目标与受理结果；只出现当前可用动作，错误保留输入 |
| 统计/成长 | 精灵位置、已有成长与成就规则 | 可读性与数据口径纠正，暂无新增回顾卡 |
| 设置/帮助 | 具体选项直接进入；现有主题/备份位置 | 故障时才展现对应诊断；不增加抽象聚合菜单 |

## 分批交付及完成门槛

批次A先做有限的对照探针，不预先开发完整面板：比较“切回本应用配置”“播放器可见时通过最小悬浮入口配置”“绑定原目标后进入黑幕再操作”三条路径。每条记录查询前后会话、失活/销毁回调、目标能力和命令结果；候选路径至少重复3次，并核对是否出现停顿、焦点变化或误控另一播放器。这里只保留必要结果和时序，不归档视频标题、账号或原始通知。

暂时不在活动列表与收到销毁回调不是同一件事；判断必须结合原控制器的可用状态和请求反馈。若三条路径均无法保持有效控制，则本次保留该播放器已验证的黑幕/返回，将固定时长撤幕作为需独立实测的保底能力；暂停和片尾标记不可用，不继续投入专属面板包装成完整支持。其他播放器能力单独验收。这是探针失败后的具体收缩范围。

| 批次 | 可审查交付 | 进入下一批的条件 |
|---|---|---|
| A：证明关键路径 | 目标绑定、会话时序探针、可行性结论和最小修复包 | 当前OPPO上的哔哩哔哩真实定时路径完成；受限能力清楚记录。无法达到时先调整范围，暂停播放器专属扩展，不继续包装完整支持 |
| B：贯通主流程 | 播放器内定时面板、命令受理结果、统一结束结果 | 实际UI完成设置、修改、取消、到期、失效和返回；声音/目标/结果都按实际证据验收 |
| C：稳定和UI | 中断与恢复、三个重点页面定稿、完整适配 | 核心流程持续稳定；动态页面和旧数据迁移通过；视觉定稿经实际预览评审 |
| D：性能与发布候选 | 分场景耗电记录、签名候选包、版本说明与验收表 | 当前已用设备/播放器通过其声明能力；未测厂商/播放器明确不纳入已支持清单；发布操作另按用户指令执行 |

每批保留独立候选APK和失败/修复证据，避免一次混入核心、外观、统计、精灵和备份重构。工期先由批次A的真实兼容结果校准，不给未经验证的固定完成日期。

### 必须覆盖的真实操作

- 启动→播放器播放→悬浮球→黑幕→返回，实际确认声音与画面。
- 从实际界面设置1分钟定时，确认受理，等到到期，检查原播放器反馈与声音；15/30/60分钟核对界面和服务deadline，不需要为了每个预设空等一小时。
- 至少一次30分钟与一次2小时连续使用；若以睡前过夜为主版本卖点，还须一次过夜实测。没有记录则保留未测。
- 显式目标失效、双播放器、配置期间会话变化、权限撤销、取消/延长/停止以及来电/耳机与到期碰撞。
- 片尾按实际播放器数据测试暂停、拖动、倍速和换集；没有有效数据就不提供该能力。
- 从已发布v4.3.1和当前v5.0.1升级；旧备份、失败恢复与成长/成就/佩戴回归。
- 每个主要动态面板：窄屏/横屏、默认/大字体、浅深色、中文与长译文；不仅截图，还检查按钮是否可达和可点击。

暂未有其他厂商真机时，只交付已测范围的候选，不借模拟器扩展兼容性结论。有人参与时，建议让3–5位未看说明的人完成基本流程；未进行则标为待评估，不编造体验成功率。

## 避免重演的具体约束

1. 每个新功能先说明用户问题、触发入口、完成结果和失败行为，不能仅写模块名称。
2. 同一个版本只变更已审阅范围；v4主按钮语义、三个页签、精灵位置不顺带改变。
3. 关键播放器可行性在UI扩展前验证；支持到哪项就写哪项，不把声明PAUSE等同实际暂停成功。
4. 单测证明逻辑、原生测试证明组件/合成行为、真机证明本次兼容路径、用户评审证明体验认可，分别留证。
5. 上一批没有达成完成门槛，先解释差异并调整范围，后续工作不覆盖掉未解决项。

## 平台依据与实现取舍

- [MediaSessionManager 官方文档](https://developer.android.com/reference/android/media/session/MediaSessionManager)：活动会话获取有权限与会话条件。基于此推断，保留控制器能减少重复发现，但不能让已销毁/未提供的会话重新可控；第三方支持仍需实测。
- [前台服务后台启动限制](https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start)：target Android15+使用悬浮窗这一豁免时还要求可见悬浮窗；后台恢复设计需逐条匹配适用条件，而不是笼统依赖悬浮窗权限。
- [唤醒锁最佳实践](https://developer.android.com/develop/background-work/background-tasks/awake/wakelock/best-practices)：持锁会耗电，获取和释放逻辑应简单并确保释放。当前服务启动即持锁，因此先测空闲成本再改，保留ROM稳定性的验证。

以上依据不推出“更换Media3、全局媒体键或增大权限即可解决哔哩哔哩兼容”的结论。主版本以明确的能力和实测结果收口。
