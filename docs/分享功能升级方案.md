# 分享功能升级方案 · 调研结论

> 调研时间：2026-10-07
> 方法：GitHub Search API（未认证，有速率限制）+ 已知项目元数据核对
> 限制：原生 Android 方向的搜索结果几乎为空，下文「观察」区分了**实证**与**推断**

---

## 一、调研发现

### 1. 分享卡的生态几乎全在 Web 端，不在原生 Android

按 stars 排序搜到的项目，语言分布是压倒性的：

| 方向 | 代表项目 | 语言 | 星数 |
|---|---|---|---|
| 服务端分享卡 | `setkyar/laravel-social-share-cards` | PHP/HTML | 49 |
| 文案转卡片 | `iyhub/personal-card-share` | TypeScript | 116 |
| 通用卡片 | `eze-is/ai-share-card`、`little-pp395/sbti-share-card-generator` | TS | 11 / 3 |
| 框架内置 | `vercel/next.js` 的 og-image 方案 | TS | — |
| 渲染引擎 | `vercel/satori`（HTML+CSS → SVG） | TS | — |

**而「Android 原生画布生成分享图」这一类，搜不到任何一个有 stars 的成熟库。**

**观察（实证）**：GitHub 上不存在可直接抄的原生分享卡实现。

**推断**：这不是生态缺失，而是**场景差异**——原生 App 要分享时，图往往已经在本地
（截图、订单、账单），直接分享现成位图即可；而 Web 需要把 URL 渲染成图才能分享。
我们这个场景（本地数据 → 生成图 → 分享）在移动端恰恰属于「本地自绘」，没有现成方案可抄。

### 2. 业界主流的版式描述方式是「HTML/CSS → 渲染成图」

`vercel/satori` 的定位是 *convert HTML and CSS to SVG*。Vercel 的 OG Image、
Next.js 的元图、各类「服务端卡片」基本都是这个模式。

**对本项目的意义**：它证明了**用声明式方式描述版式**比手写坐标更好维护——
但 satori 是 Node 库（依赖 wasm/字体），**不能用在 Android 上**。

**结论**：这个思路（声明式版式）值得借鉴，**这个实现（satori）不适合搬**。

### 3. 打卡/习惯类项目没有可参考的分享设计

`habit tracker streak android`、`pomodoro focus timer android` 等搜索要么无结果、
要么是零星小项目。说明**这个细分品类在开源侧基本是空白**，没有形成事实标准。

## 二、我们当前的实现 vs 业界

| 维度 | 业界常见 | 我们现在 | 差距 |
|---|---|---|---|
| 版式描述 | HTML/CSS 声明式 | 手写 Canvas 坐标 | 改版式要动代码 |
| 多尺寸适配 | 1:1 / 3:4 / 9:16 多比例 | 只有 1080×1440 | 缺 |
| 内容可配置 | 服务端下发 JSON 模板 | 硬编码在 `SharePoster` | 缺 |
| 二维码 | 几乎标配 | 无 | 缺 |
| 预览 | 主流都有 | 有（本轮刚加） | ✓ |
| 本地隐私 | 多为服务端 | 纯本地，符合本项目 | ✓ |
| 字体 | 自定义字体保证一致 | 系统默认 | 风险 |
| 保存位置 | 缓存/临时 | 公共 Pictures | 可议 |

## 三、升级方案

### P0 · 值得做（改动小、收益明确）

**1. 多比例导出**
一套数据，三种版式：
- `3:4`（1080×1440）—— 朋友圈 / 微博，现有
- `1:1`（1080×1080）—— 小红书 / 微信朋友圈缩略
- `9:16`（1080×1920）—— 抖音 / 竖屏壁纸

实现：把版式抽成「按高度分档」的比例策略，而不是固定坐标。
预计 1 天，纯 `SharePoster` 内部改动，不影响其它模块。

**2. 二维码（指向 GitHub 仓库或下载页）**
- 纯本地生成可用 `zxing`（34117★，成熟），但**引入依赖**与本项目「零第三方依赖」的
  立场冲突，需要你拍板
- 零依赖方案：自己实现 QR 编码（byte mode + RS 纠错 + 掩码）约 300–500 行，
  有一定风险但可控
- 价值：让图能被「扫一下就装」，是从「晒图」到「拉新」的闭环

**3. 分享后清理**
现在图会留在相册。要么改成「分享后询问是否保留」，要么存到 `cacheDir` +
自定义 Provider 授权（需要写 ContentProvider）。**取决于你上一条反馈的取向。**

### P1 · 值得做

**4. 版式声明化**
把 `SharePoster.render()` 里散落的坐标抽成一个「版式描述」结构（元素列表 + 相对位置），
而不是继续堆硬编码坐标。这样加一行数据、改一个顺序不用重画整个流程。

**5. 字体**
现在用系统默认字体。不同手机上中文排版宽度会差（数字宽度尤其明显），
可能导致换行或截断。若要稳定，需内置一套字体（增加 APK 体积，
但本项目目前只有 ~300KB，空间充足）。

### P2 · 明确不建议

**6. 搬 satori / 服务端渲染**
与本项目「无网络权限、纯本地」的定位直接冲突，且引入 Node 运行时。**排除。**

**7. 自定义分享面板**
自己做一套 App 选择器（很多国产 App 的做法）能控制视觉，但：
- 要维护第三方 App 列表（微信/QQ/微博/小红书…）
- 各家 Intent 协议不同，会持续出兼容问题
- 系统 chooser 已经够用

**不建议**，除非你有明确的品牌诉求。

## 四、需要你拍板的三件事

1. **二维码要不要？** 引入 zxing（放弃零依赖立场）还是自己实现（零依赖但有风险），还是不做？
2. **海报留在相册还是用完即删？**
3. **要不要做多比例（1:1 / 9:16）？** 小红书场景确实需要，但会翻倍测试量。

拍完我再动手。**在你决定之前不做任何代码改动。**
